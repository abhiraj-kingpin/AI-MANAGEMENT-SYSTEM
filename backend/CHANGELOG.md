# Changelog

All notable backend development history, in build order. The [README](README.md) describes the system as it stands today; this file explains how it got there — including every deliberate simplification, every bug a test caught before it shipped, and the reasoning behind each.

Format loosely follows [Keep a Changelog](https://keepachangelog.com/). Test counts are cumulative (`npm test`, no live MongoDB required for any of them).

## [v1.1.9] — Real Accuracy Measurement (LFW) Fixes a Broken Threshold, Plus Real Anti-Spoofing

Two additions, both closing gaps this project's own README has flagged since `v1.1.6`: face recognition had no measured accuracy, and no defense against a printed-photo or screen-replay registration.

**`scripts/lfw-eval.ts`** — a real, runnable evaluation script (`npm run eval:lfw`) that runs this backend's actual `generateFaceEmbedding`/`cosineSimilarity` pipeline against LFW (Labeled Faces in the Wild), the standard academic face-verification benchmark, using its own standard `pairsDevTest.txt` split (500 same-person + 500 different-person pairs, a fixed published split, not randomly sampled). The dataset itself (real people's photos, even a long-standing ethically-established benchmark) is deliberately never committed to this repo — same reasoning as the one CC0 portrait used to manually verify SCRFD detection in `v1.1.7` — the script reads it from a local, gitignored directory instead, with download URLs and checksums in its own doc comment (verified against `scikit-learn`'s own `_lfw.py`, the same mirror `sklearn.datasets.fetch_lfw_pairs` uses).

**Real run results** (989/1000 pairs processed; 11 skipped for no detectable face in at least one image — a real, expected SCRFD failure rate, not swept under the rug):

| threshold              | accuracy                    | FAR       | FRR    |
| ---------------------- | --------------------------- | --------- | ------ |
| 0.10                   | 94.24%                      | 6.04%     | 5.49%  |
| 0.20                   | 96.66%                      | 0.60%     | 6.10%  |
| **0.24**               | **96.97%** (empirical best) | **0.00%** | 6.10%  |
| 0.30                   | 96.76%                      | 0.00%     | 6.50%  |
| 0.50                   | 91.61%                      | 0.00%     | 16.87% |
| 0.70                   | 60.57%                      | 0.00%     | 79.27% |
| **0.85** (old default) | **51.16%**                  | 0.00%     | 98.17% |
| 0.90                   | 50.35%                      | 0.00%     | 99.80% |

Mean same-person similarity: 0.588. Mean different-person similarity: 0.003.

**The finding that actually matters**: `FACE_MATCH_THRESHOLD`'s default (0.85, an unmeasured guess from before this codebase had a real embedding model at all) scores 51.16% on this benchmark — statistically indistinguishable from a coin flip. It would have rejected the overwhelming majority of genuine check-ins (98.17% false-reject rate) in real use. This had been sitting in `config/env.ts` undetected because nothing before this pass ever measured it against real labeled data. Fixed to `0.3` — inside the threshold range (0.24–0.85) where measured false-accept rate was exactly 0%, with deliberate headroom above the razor's-edge empirical optimum (0.24) rather than sitting exactly on it, since a single finite benchmark's exact peak is more likely to be slightly optimistic than a point a little further into the flat, still-0%-FAR region. See `config/env.ts`'s own comment for the same reasoning, shorter.

**What this does and doesn't prove**: real, honest evidence that the detect→align→embed→cosine-match pipeline is genuinely discriminative for real faces (this was previously unverifiable — no dataset of real people existed in this environment at all). Not a substitute for measuring this specific deployment's own employees under this specific deployment's own camera conditions — LFW is mostly well-lit, front-facing, professional photos of public figures, a real but imperfect proxy.

**`livenessDetector.ts`** — real single-image presentation-attack detection (PAD), wired into `face.service.ts#register()`'s per-photo loop (a registration photo that fails this check is discarded the same way a low-quality or faceless one already is, not silently accepted). Model: MiniFASNet-V2 (`minifasnet_v2.onnx`, 1.7MB), an ONNX export (Apache 2.0, same license as the upstream) of `minivision-ai/Silent-Face-Anti-Spoofing`'s `2.7_80x80_MiniFASNetV2.pth`, downloaded from `garciafido/minifasnet-v2-anti-spoofing-onnx` on Hugging Face — provenance verified via checksum (both the ONNX file and, per that repo's model card, the original upstream `.pth` it was losslessly converted from) before use, not assumed. Preprocessing (the 2.7×-margin crop-around-bbox-center) is a direct, variable-for-variable port of upstream's own `CropImage._get_new_box`/`crop` (`src/generate_patches.py`) — fetched and read before writing this repo's version, the same discipline `faceDetector.ts`'s anchor decoding and `faceAlign.ts`'s reference template already followed, given how easily a silently-wrong crop formula produces a plausible-but-meaningless liveness score. One documented approximation: the crop-to-80×80 resize is this repo's own from-scratch bilinear implementation (reusing `faceAlign.ts`'s already-tested `bilinearSample`) using OpenCV's documented half-pixel-center coordinate mapping for `INTER_LINEAR`, not verified byte-for-byte against a real `cv2.resize` call (no OpenCV/Python in this environment) — the same class of gap `faceAlign.ts`'s own warp had before it shipped.

This is a different, complementary signal from the mobile app's existing blink-based liveness check (`BlinkLivenessChecker`): that one is temporal (a real eye-open→closed→open sequence across several frames, catches a static photo trivially, but could in principle be fooled by a video replay that itself shows blinking) and runs client-side at check-in; this one is single-image texture/reflection/moiré analysis with no notion of motion at all, and runs server-side at registration. Neither replaces the other, and this one does NOT run at check-in (the backend's `verify()` only ever receives a pre-computed embedding vector from the client, never a raw image — mobile's blink check remains the only check-in-time liveness signal).

No labeled real-vs-spoof dataset exists in this environment either (LFW, used above, is entirely genuine photos — it has no print/replay-attack examples), so `LIVE_THRESHOLD` (0.5, the natural "which class wins" cut for a 3-class softmax) is real but unverified the same way `FACE_MATCH_THRESHOLD` used to be — documented as such in `livenessDetector.ts`'s own comment rather than left silent.

**Verified**: 614 Jest tests (up from 608 — 4 new: `detectLiveness`'s own real-inference suite, merged into `faceRecognitionModels.test.ts` rather than a separate file, for the exact same reason that file's own doc comment already explains — a fourth Jest file independently touching `onnxruntime-node` would reintroduce `v1.1.8`'s SIGABRT bug; plus 2 new tests in `face.service.test.ts` for the discard-on-failed-liveness path, mocked there the same way `generateFaceEmbedding` already was). `tsc`, `eslint`, `prettier` all clean. `scripts/lfw-eval.ts` was actually run against the real dataset, twice (the second run added a fuller threshold sweep and cached raw per-pair results so a future threshold reconsideration never needs to re-run the ~15-minute real-inference pass) — the numbers above are real output, not illustrative.

## [v1.1.8] — CI Caught a Real Crash in v1.1.7: Two Jest Files, One Native ONNX Runtime Singleton

`v1.1.7`'s 608 tests all passed locally, repeatedly — but `npm test` aborted on CI with exit code 134 (SIGABRT), a native crash, not a normal assertion failure. `docker-build` never even ran as a result.

**Finding it took two wrong turns before the real cause, and both are left in this history rather than quietly skipped over.** The standard GitHub annotations API only surfaces short messages, not real command output, so a temporary CI step was added to route `npm test`'s actual stdout+stderr through `::error::` annotations (removed again once the real cause was found). First attempt emitted the log top-down and only ever showed the first few `PASS` lines — GitHub caps `::error::` annotations at roughly 10 per step, so only the front of a ~600-line log ever got through; fixed by grepping the whole log for the informative lines (`PASS`/`FAIL`, stack frames, abort messages) and keeping the last matches instead, which surfaced a real native abort inside `onnxruntime-node`'s own init path (`initOrt` → `OnnxruntimeSessionHandler` → `backend.js:136`), happening the moment the face-recognition tests loaded their first real model.

**Wrong turn**: this repo already had one confirmed case of the identical _symptom_ — `ci-admin.yml` needed Node 20 → 22 because Vitest 4.x's `undici` dependency doesn't work on Node 20. Reasonable hypothesis, and cheap to test — `ci-backend.yml` bumped to Node 22. The crash reproduced identically. Wrong hypothesis, honestly reverted in spirit if not in the version number (Node 22 is still the correct floor regardless — see below — it just wasn't _this_ fix).

**The actual cause**: `onnxruntime-node`'s native binding module (`binding.js`) guards its one-time native environment init with a plain module-scoped `let ortInitialized = false`. That guard only means "once per copy of this module" — and Jest gives every test _file_ its own fresh module registry, so `faceDetector.test.ts` and `faceEmbedding.provider.test.ts` (two separate files, each creating a real `InferenceSession` for its own model) each got their own independent copy of that guard, each starting at `false`. Both therefore called the real, underlying native `initOrtOnce()` — which registers a native environment cleanup hook. The second registration collided with the first (same process, same native environment, genuinely already registered), and Node's own internal duplicate-registration assertion in `CleanupQueue::Add` fired — a hard process abort, not a catchable JS exception, not something any try/catch around `InferenceSession.create()` could ever have caught. Confirmed by reproducing the exact same crash locally (not CI-only) once actually looked for by running the two files together, and reading the real native assertion message in the output rather than continuing to guess.

**The fix, in two parts**:

1. `faceDetector.test.ts` and `faceEmbedding.provider.test.ts` merged into one file, `faceRecognitionModels.test.ts` — the only way for `onnxruntime-node`'s "once" guard to actually mean once is for both real sessions to be created inside the _same_ Jest module registry. The merge forced `faceEmbedding.provider.test.ts`'s detector fake to move from `jest.mock('.../faceDetector', ...)` (replaces the whole module with a different fake instance — would have silently reintroduced the identical two-copies problem) to `jest.spyOn(faceDetectorModule, 'detectFaces')` on the one real, shared import, restored after every test. Net effect on coverage: none — same test count, same assertions, same real-vs-mocked boundaries.
2. Both `faceDetector.ts` and `faceEmbedding.provider.ts`'s `getSession()` now pass explicit `{ executionMode: 'sequential', intraOpNumThreads: 1, interOpNumThreads: 1 }` — `onnxruntime-node` has multiple open upstream reports of non-deterministic native crashes tied to its own thread pool during session init on Linux (`microsoft/onnxruntime` #23794, #20084); these are small CPU models on a request path nowhere near latency-sensitive enough to need ORT managing its own thread pool, so this trades a sliver of theoretical parallelism for removing an entire class of native non-determinism.

**Left in place, still correct on their own merits**: `ci-backend.yml` and `Dockerfile` stayed on Node 22 (`package.json#engines` now correctly says `>=22`, not `>=20`) — not because it fixed this bug, but because there's no reason to run older Node than the fix was tested under, and the `Dockerfile` bump closes a real separate gap: `docker-build` in CI only proves the image _builds_, it never runs it, so a crash like this could ship straight into a deployed container and only surface the first time a real user tried to register or verify a face in production.

**Verified**: same 608 tests (test _files_ count dropped by one from the merge, not test count), 4 consecutive clean local runs confirming this isn't just non-reproducing-by-luck, plus `lint`/`format:check`/`typecheck`/`build` all clean — and, this time, actually confirmed green on CI's Linux runner before calling it done, not just asserted.

## [v1.1.7] — Real Face Detection + Alignment (SCRFD), Closing v1.1.6's Own Gap

`v1.1.6` shipped a real embedding model but flagged its own biggest remaining gap honestly: no face detection, no alignment — the whole photo got resized straight into the model instead of a cropped, aligned face region. This closes it, with the same `buffalo_s` pack's bundled detector `v1.1.6` deliberately left out.

**Added — `faceDetector.ts`**: real face detection via `det_500m.onnx` (SCRFD, same InsightFace `buffalo_s` pack, same MIT license and provenance as the embedding model — see `v1.1.6`'s entry). Finds every face-like region in a photo with a confidence score, bounding box, and 5 landmarks (eyes, nose, mouth corners). Anchor generation, bbox/keypoint decoding (`distance2bbox`/`distance2kps`), and the score/NMS thresholds all mirror InsightFace's own `scrfd.py` — fetched and read directly from InsightFace's GitHub repo before writing a single line of decode logic, not derived from memory or a paraphrased summary of it, given how easily a silently-wrong anchor/output-index mapping could produce plausible-looking-but-meaningless detections. The 9-output configuration (3 strides × {score, bbox, keypoints}) and the exact output-to-stride index mapping were cross-checked against this exact model's real output shapes (each stride's output row count exactly matches its expected anchor count: 80×80×2=12800 for stride 8, etc.) — a second, independent confirmation beyond just reading the source.

**Added — `faceAlign.ts`**: the standard InsightFace 5-point similarity-transform alignment (warping detected landmarks onto InsightFace's fixed reference template, `arcface_dst` — also fetched directly from `face_align.py`, not guessed) — the alignment MobileFaceNet was actually trained on, not a bounding-box crop. Solved the least-squares similarity-transform estimation in closed form via a complex-plane fit rather than implementing a general 2×2 SVD (Umeyama's algorithm, what `skimage.transform.SimilarityTransform` uses) — mathematically equivalent for this case (no reflection ever needed for real face landmarks against this template), and avoids needing a full numerical SVD for a branch that would never execute. The actual pixel warp (bilinear inverse-sampling) is a from-scratch implementation, not a call to `sharp`'s `affine()` — its exact geometric convention (matrix direction, translation handling) wasn't confidently knowable without risking a subtly-wrong crop, and a self-contained implementation is directly unit-testable against known-answer geometry instead.

**Testing philosophy note**: `faceAlign.ts`'s math is pure geometry with no model or real photo dependency, so it's fully, rigorously verified — known-answer test cases (identity, a known 2× scale, a known 90° rotation, a known translation, all with hand-computed expected results) confirm the derivation is actually correct, not just "runs". `faceDetector.ts` was additionally verified once, manually, against a real CC0-licensed portrait photo (downloaded temporarily, never committed to this repo — distributing an identifiable person's photo in a public repository isn't appropriate even under a permissive license): one correct detection, a bounding box that visually matched the face in the photo, anatomically plausible landmarks. `faceDetector.test.ts`'s automated suite covers what's honestly verifiable without a real face on file: a flat/featureless image produces zero detections (a real, meaningful negative case — nothing face-like exists in it), determinism, output shape sanity, and non-square images not crashing the resize/pad math.

**Wired into the embedding pipeline**: `generateFaceEmbedding` now detects first, picks the highest-confidence face if more than one appears, aligns it, and only then runs the embedding model — instead of resizing the whole photo. Added `NoFaceDetectedError`, thrown when detection finds nothing; `face.service.ts#register()` catches it and discards that photo the same way it already discarded a low-quality one, rather than letting a faceless photo crash the whole registration request. `faceEmbedding.provider.test.ts`'s old flat-color fixtures stopped being useful for exactly the reason this change is real: a flat color genuinely has no face, so real detection now correctly rejects them. Restructured to mock `detectFaces` (already independently, thoroughly tested in its own file) and focus this file's tests on what's actually its own concern — alignment integration, normalization, embedding shape, and a real test proving the highest-scoring detection is actually the one used when more than one face is found (not just that multiple detections don't crash it).

**Verified**: 608 Jest tests (up from 589 — 9 new in `faceAlign.test.ts`, 5 in `faceDetector.test.ts`, 3 more in `face.service.test.ts` for the discard-on-no-face path, `faceEmbedding.provider.test.ts` restructured with the same net test count). `tsc` clean, `eslint` clean, `prettier` clean, `npm run build` clean, plus a direct smoke test against the compiled `dist/` output (not just `ts-jest`) confirming the full detect→align→embed pipeline runs correctly outside the test harness too.

## [v1.1.6] — Real Face Embedding Model (MobileFaceNet via ONNX Runtime)

**Added** — `POST /face/register`'s photo→vector step now runs a real, trained neural network instead of hashing image bytes. `faceEmbedding.provider.ts` loads [InsightFace's official `buffalo_s` model pack](https://github.com/deepinsight/insightface/releases/download/v0.7/buffalo_s.zip) (MIT license) — specifically `w600k_mbf.onnx`, a MobileFaceNet model — via `onnxruntime-node`, preprocesses the uploaded photo with `sharp` (resize to 112×112, RGB, `(pixel-127.5)/128` per InsightFace's own documented normalization), runs real inference, and L2-normalizes the 512-dimensional output.

- Model committed at `backend/models/w600k_mbf.onnx` (13.6MB, SHA-256 `9cc6e4a75f0e2bf0b1aed94578f144d15175f357bdc05e815e5c4a02b319eb4f`). Input shape `[1,3,112,112]`, output `[1,512]` — both confirmed by actually running inference against this exact file (`ort.InferenceSession` + a dummy tensor), not assumed from documentation.
- **Deliberately scoped to embeddings only, not face detection.** The whole uploaded photo is resized straight to the model's input — not a detected-and-cropped face region. The same `buffalo_s` pack bundles a real face detector (`det_500m.onnx`, SCRFD, 2.5MB) that was deliberately left out: correctly decoding SCRFD's raw anchor-based output (anchor generation per stride, score thresholding, NMS) is real implementation work this environment has no way to verify against real photos with known face locations. Confirmed this scoping decision with the user before downloading anything, given the real tradeoffs (binary provenance/trust, repo size, and — the most important one — that even a perfect implementation can't be verified to actually recognize faces correctly here: no photos of real people with known identities exist in this environment to test against).
- **Real bug caught by reading the code before shipping, not by a test failing**: `analytics.ai.service.ts`'s `duplicate_face` anomaly sweep pairwise-compares every active `FaceEmbedding` org-wide via `cosineSimilarity`, which correctly throws on a length mismatch. With three embedding spaces now realistically coexisting in one deployment (512-d real model, 67-d mobile's on-device geometric placeholder, 128-d from anything registered before this model existed), that sweep would have crashed the instant two employees registered through different paths — a pre-existing latent bug this change made newly likely to trigger, not something this change introduced. Fixed by skipping mismatched-length pairs (they were never comparable anyway) and making each flagged anomaly's `detail` field say which kind of comparison it actually is.
- **`FaceEmbedding.vector`'s doc comment corrected** while touching the file: it already anticipated "128-d (ML Kit) or 512-d (TFLite FaceNet-style model)" but neither matched reality (mobile's actual placeholder is 67-d geometric, not 128-d ML Kit) — now says what's actually true for each path.
- **Test fixtures changed shape**: the old placeholder hashed arbitrary bytes, so `faceEmbedding.provider.test.ts` fed it garbage (`Buffer.from('image-one')`); a real image-processing pipeline rejects that outright. Fixtures are now tiny synthetic flat-color JPEGs generated with `sharp` itself at test time. `face.service.test.ts` was unaffected — it already mocked this module entirely.
- **Real Jest+native-addon bug found and fixed, not worked around**: `faceEmbedding.provider.test.ts` deliberately runs the real model unmocked (mirroring `GeometricEmbeddingGenerator`'s own real test on the mobile side) and initially failed with `TypeError: A float32 tensor's data must be type of function Float32Array()` — a documented, Jest-maintainer-"closed as not planned" limitation (`jestjs/jest#11864`): Jest's sandboxed test realm gives each file its own `Float32Array` constructor, and `onnxruntime-node`'s native tensor validation checks identity against the real process's. Confirmed by running the exact same code successfully outside Jest first. Fixed with a custom Jest environment (`tests/utils/realGlobalsNodeEnv.js`) that rebinds the sandbox's typed-array constructors to the real ones, scoped to only this one test file via a `@jest-environment` docblock.
- **Dockerfile fixed for two real deployment risks**: switched every stage from `node:20-alpine` to `node:20-slim` — `onnxruntime-node` ships no musl-compiled binary and fails outright on Alpine (confirmed via [documented upstream issues](https://github.com/microsoft/onnxruntime/issues/2909), not a guess); `sharp` and `bcryptjs` are unaffected either way. The runtime stage now also copies `backend/models/` into the final image, which it never did before (only `dist/` was copied, and `tsc` never touches non-TypeScript files). This environment has no Docker to build/run the image interactively, but `ci-backend.yml`'s `docker-build` job does exactly that on every push (`needs: lint-typecheck-test-build`) — it passed on this exact commit, confirming both fixes on real infrastructure rather than leaving them as documented-but-unverified.
- **`npm audit`**: two low-risk transitive vulnerabilities left as-is rather than force-fixed — `adm-zip` (via `onnxruntime-node`'s install-time platform-binary extraction, a DoS-only issue not exploitable here since it only ever extracts the package's own bundled archive) and `uuid` (via `exceljs`, pre-existing before this change). `npm audit fix --force` would downgrade both to older/prerelease versions, a worse trade than the actual risk.

**Verified**: 589 Jest tests (up from 588), including real (unmocked) ONNX inference in `faceEmbedding.provider.test.ts` and a smoke test run directly against the compiled `dist/` output (not just `ts-jest`) confirming the exact same path-resolution math works in both dev and production layouts. `tsc` clean, `eslint` clean, `prettier` clean, `npm run build` clean.

## [v1.1.5] — Leave Carry-Forward, Absence Sweep, Analytics PDF Export, Connection Pool

Closes three of the four gaps `README.md`'s "Other known, documented gaps" section had been flagging since Phase 8/17, found while doing a full pass over every documented placeholder/gap in the repository ahead of a status review.

**Added — `POST /leaves/carry-forward`** (`leaveCarryForward.service.ts`): computes each active employee's unused balance for every `LeaveType` with `carryForward: true`, capped at `maxCarryForwardDays`, and writes it into next year's `LeaveBalance.carriedForward`. `LeaveType.carryForward`/`maxCarryForwardDays` and `LeaveBalance.carriedForward` have existed in the schema since Phase 2 and were read everywhere balance math happens — nothing had ever computed a value into that field. Idempotent (`$set`, not `$inc`) and, importantly, correctly covers employees with **no** persisted `fromYear` balance row at all (anyone who took zero leave that year) by iterating every active employee explicitly rather than only rows that happen to exist — those are exactly the employees with the most to carry forward, and the easiest case for a naive implementation to silently skip. Real bug caught while designing this, before any test ran: an early draft only iterated existing `LeaveBalance` rows and would have produced a $0 carry-forward for anyone who never took leave.

**Added — `POST /attendance/absence-sweep`** (`absenceDetection.service.ts`): marks every active employee with no Attendance record for a date `absent` — the status has existed in `Attendance.status`'s enum since Phase 5, unused by any code path until now. Skips weekends/holidays via the same `listBusinessDays` business-day math leave balances already use. Uses per-employee `updateOne` + `$setOnInsert` + `upsert: true` rather than `insertMany`, mirroring `leave.service.ts#markAttendanceOnLeave`'s exact race-safety reasoning: a real check-in landing concurrently between the sweep reading "who's missing" and writing the absent stub always wins, never gets overwritten.

**Added — `GET /analytics/export/pdf`**: the PDF counterpart to the existing `/analytics/export/csv`, sharing a newly-extracted `fetchExportRecords()` helper (same employee-filter + date-range query, same 5,000-row cap) and mirroring `attendance.service.ts#exportPdf`'s existing PDFKit layout convention rather than inventing a second one. Reuses `/export/csv`'s existing query schema — the shape (`from`/`to`/`departmentId`) has nothing CSV-specific about it.

**Added — explicit Mongoose connection-pool sizing** (`MONGO_MAX_POOL_SIZE`/`MONGO_MIN_POOL_SIZE`, defaults 20/2, `config/database.ts`) in place of the driver's defaults (100/0). Honesty note: the actual throughput effect is unverified — this environment has no live MongoDB to run a concurrent-connection load test against, so this is a documented config change, not a measured tuning result. `perf:smoke`'s sequential-latency-only limitation stays exactly as documented.

**Deliberately not touched**: the fourth gap in that section — one `clientGeneratedId` per attendance document instead of one per punch type. The real fix touches `attendance.service.ts`'s check-in/check-out/sync paths in several places at once, in a codebase with no live MongoDB available here to verify a schema-shaped change against end-to-end. Left as a documented, already-mitigated gap (see README) rather than risk a subtle regression in well-tested idempotency logic that can't currently be re-verified live.

**Verified**: 588 Jest tests (up from 569 — 19 new: 4 carry-forward service + 4 carry-forward route + 4 absence-sweep service + 3 absence-sweep route + 2 PDF-export service + 2 PDF-export route), `tsc` clean, `eslint` clean, `prettier` clean, `npm run build` clean.

## [v1.1.4] — Face Registration: Accept Client-Computed Embeddings

**Added** — `POST /face/register-embeddings`, a second registration path for the same feature `POST /face/register` already served, motivated by real work on the mobile side: the mobile app's new face check-in (see [`mobile-app/CHANGELOG.md`](../mobile-app/CHANGELOG.md)) computes a 67-number embedding on-device from ML Kit face-landmark geometry, structurally unrelated to `faceEmbedding.provider.ts`'s image-byte hash that `/register` produces server-side. An employee registered through the original photo-upload path could never cosine-match a check-in embedding the phone computed — not a hypothetical, a documented "Known Limitation" in the mobile-app README the moment face check-in shipped. This endpoint lets a client submit 3–5 embeddings it already computed itself, so both ends of one employee's face data can be generated the same way.

- `registerFaceEmbeddingsSchema` (`face.validators.ts`): `embeddings: z.array(z.array(z.number()).min(64).max(1024)).min(3).max(5)` — same 3–5 reference-set size and 64–1024 dimension bounds as every other face-embedding contract in this codebase (`checkInSchema`, `verifyFaceSchema`), just applied to a batch.
- `faceService.registerWithEmbeddings()`: stores one `FaceEmbedding` row per submitted vector with `qualityScore: null` and no `sourceImageUrl` (no image is ever uploaded on this path) — deliberately skips the quality-score filtering `register()` applies to server-hashed embeddings, since a client that ran real on-device face detection to produce these vectors already made its own quality decision before submitting. Reuses the same reference-set-replacement rule as `register()` — extracted the shared `deactivatePreviousEmbeddings(employeeId, keepIds)` helper out of `register()`'s inline `updateMany` call rather than duplicating it.
- `FaceEmbedding.sourceImageUrl` changed from required to optional, in both the Mongoose schema and the `IFaceEmbedding` TypeScript interface — this is the one change here that touches the existing `/register` path's data shape (not its behavior; every existing `/register` call still uploads and stores an image, so `sourceImageUrl` is always present there in practice). The doc comment on the field ties the decision back to `docs/architecture/06-tech-stack-justification.md`'s stated on-device-privacy rationale: requiring an image upload alongside a client-computed embedding would defeat the reason that architecture keeps biometric processing on-device in the first place.
- **Honesty note, not a fix**: this endpoint closes the registration/check-in mismatch only where both ends are actually wired up. The mobile app has no registration screen calling it yet — still open on the mobile-app roadmap. Until that screen exists, `/face/register-embeddings` is reachable and fully tested, but not yet exercised by the app itself.
- **Verified**: 569 Jest tests (up from 562) — 7 new cases across `face.service.test.ts` (4: stores one row per embedding with the right shape, deactivates the previous reference set, HR-on-behalf-of, cross-employee block) and `face.routes.test.ts` (3: 401 unauthenticated, 422 for fewer than 3 embeddings, 422 for an embedding shorter than 64 numbers).

## [v1.1.3] — Salary & Payslip Lists: Real Employee Names, Shared `resolveEmployeeRefs`

## [Phase 15] — AI-Assisted Analytics

**Added** — `modules/analytics/analytics.ai.*`: `GET /analytics/ai/late-risk`, `GET /analytics/ai/absenteeism-trend`, and `GET /analytics/ai/anomalies`, per the Phase 0 contract in [`docs/architecture/04-api-documentation.md`](../docs/architecture/04-api-documentation.md#analytics-analytics).

- **Named honestly**: everything here is transparent, rule-based statistics — a rate, a trend nudge, a least-squares line, a z-score, a cosine similarity — not a trained model. Every response is fully reconstructible from the numbers it also returns (`late-risk` includes `lateDays`/`workingDays`/`trend` alongside the score; the forecast literally states `method: "linear-regression"`).
- **Late-risk** (`/ai/late-risk`): ranks the caller's in-scope employees by late-arrival rate over a trailing window (7–180 days, default 30), nudged ±10 points depending on whether the second half of the window is worse or better than the first. Team-scoped for a Manager, org-wide (optional `departmentId`) for Super Admin/HR — reuses `analytics.service.ts`'s `resolveEmployeeIds`, exported for this purpose.
- **Absenteeism trend** (`/ai/absenteeism-trend`): monthly unexplained-absence rate — defined as an expected working day with no attendance signal at all (present/late/half-day/on-leave), which correctly measures real absenteeism without depending on the schema's `absent` status that nothing currently writes (see Phase 11's documented gap) — plus a one-month-ahead forecast from a least-squares trend line over the history.
- **Anomalies** (`/ai/anomalies`, HR/Admin only): three independent rule-based checks run concurrently — `location_anomaly` (haversine distance between two consecutive GPS punches, divided by elapsed time; flags implied travel over 200 km/h), `duplicate_face` (pairwise cosine similarity ≥0.92 between two _different_ employees' face embeddings, reusing the same real `cosineSimilarity` math Phase 8 already tests), and `overtime_outlier` (a **leave-one-out** z-score on trailing-window overtime totals — see the real bug this caught, below).
- **Real bug caught while building this phase**: a self-inclusive z-score (each employee scored against the mean/stddev of the _whole_ group, including themselves) mathematically caps the highest possible z-score at `sqrt(n-1)` — a lone outlier drags the group's own mean/stddev up enough to partly hide itself. With small teams this silently made the outlier check nearly impossible to trigger (a 4-person sample can never exceed z≈1.73, below the z>2 threshold, no matter how extreme the outlier). Caught by a test asserting a deliberately extreme case _should_ have been flagged and wasn't. Fixed by scoring each employee against a "leave-one-out" baseline (mean/stddev of everyone _else_) instead — the standard fix for small-sample outlier detection.
- `duplicate_face` explicitly inherits Phase 8's documented placeholder in its own `detail` field: the embeddings it compares are hashed image bytes (no GPU/model runtime in this environment), so a flagged pair means "similar-looking source photos," not confirmed shared identity.
- New `shared/utils/geo.ts#haversineDistanceKm` — a plain great-circle-distance function for comparing two in-memory GPS points directly, distinct from `geofence.service.ts`'s `$geoNear` (which only works against an indexed collection).
- **Verified**: 482 Jest tests (up from 458 — 24 new, split across `analytics.ai.service.test.ts` (real statistics, hand-computed) and `analytics.routes.test.ts`'s new RBAC/validation cases).

**Added** — `modules/shifts/`: shift definitions (morning/night/rotational/flexible), single and bulk employee assignment, and `GET /shifts/me`.

- Assignments are forward-only by design (`effectiveFrom` must be today or later) — there is always at most one open-ended assignment per employee, so reassigning just closes the previous one out the day before, with no arbitrary-interval reconciliation needed.
- `attendance.service.ts` now resolves each employee's real assigned shift for late/present at check-in and overtime/half-day thresholds at check-out, correctly handling night shifts that cross midnight — falling back to the old hardcoded defaults only for an employee nobody's assigned a shift to yet, which is what let every pre-existing attendance test keep passing unchanged.
- Half-day threshold now scales with the shift's real duration instead of a flat 4 hours.
- **Verified**: 329 Jest tests (up from 284).

## [Phase 9] — Leave Management

**Added** — `modules/leaves/`: apply/cancel/approve/reject, running balances, leave types, and a holiday calendar.

- `totalDays` is computed server-side from real business-day math (`shared/utils/businessDays.ts`), excluding weekends and holidays — never trusted from the client.
- Balances are lazy: no `LeaveBalance` document is written until a request is actually approved or reversed; before that, the balance is computed virtually from the leave type's default quota.
- Approving a leave stamps real `on_leave` Attendance records for each business day (via `$setOnInsert`, never overwriting a real check-in); check-in now rejects with `ON_APPROVED_LEAVE` on a day already stamped that way.
- The manager-scoping query attendance already had inline was extracted to a shared `getManagedEmployeeIds` helper instead of being copy-pasted a third time.
- **Flagged gap**: `LeaveType.carryForward`/`maxCarryForwardDays` are schema fields the balance math reads, but nothing automates the year-end carry-forward computation yet — that needs a scheduled job.
- **Verified**: 284 Jest tests (up from 218).

## [Phase 8] — Face Recognition

**Added** — `modules/face-recognition/`: registration, per-employee embedding storage, cosine-similarity verification wired into check-in as `method: 'face'`.

- **One seam is a labeled placeholder, confirmed with the user before building, not a silent one.** Converting a photo into an embedding vector needs a real face-recognition model (FaceNet/MobileFaceNet), which can't run in this backend-only environment (no GPU, no model bundling). `faceEmbedding.provider.ts` deterministically hashes image bytes into a unit vector instead — loudly documented as having no relationship to actual facial similarity, existing only so the pipeline around it is exercisable end-to-end. Swapping in a real model is a one-function change.
- Everything around that seam is real: attendance-time verification never touches an image (the mobile app computes the embedding on-device per the architecture); the backend runs real cosine-similarity math against stored embeddings, thresholded at `FACE_MATCH_THRESHOLD`. Liveness must be explicitly `true`, not merely present.
- `DELETE /face/:employeeId` is a genuine hard delete — the one place in this codebase that isn't soft-delete, since biometric data warrants real right-to-erasure.
- **Real bug caught while building**: the first draft of "deactivate old embeddings on re-registration" used a time cutoff, which could misfire mid-batch on a slow request; fixed to exclude by explicit id instead.
- **Verified**: 218 Jest tests (up from 180).

## [Phase 7] — QR Attendance

**Added** — `modules/qr/`: HR/Admin generate a time-boxed, HMAC-signed QR per branch; employees scan it via `POST /attendance/check-in` with `method: 'qr'`.

- Two independent checks close two different attack paths: the JWT's own signature + `exp` (fast-fails a forged/tampered token before any DB call), and the DB record's `validTo` (catches a token revoked before its original `exp` — the JWT alone can't see that).
- Uses its own signing secret (`QR_TOKEN_SECRET`), separate from session JWTs, since a QR code is a different trust boundary (displayed on a screen, potentially photographed).
- **Real bug the tests caught**: the "already checked in today" guard originally ran _after_ method-specific work — harmless for GPS, but QR's `validateAndConsumeQrToken` mutates the QR record as a side effect, so a doomed request would have silently burned a single-use code. Fixed by reordering the guard first.
- **Verified**: 180 Jest tests (up from 155).

## [Phase 6] — GPS Attendance

**Added** — `modules/geofence/`: office-location CRUD plus `findNearestGeofence()`, wired into check-in as `method: 'gps'`.

- A single `$geoNear` aggregation against the `2dsphere` index does the distance math and sorts nearest-first server-side — not an app-level haversine loop.
- `DELETE /geofences/:id` deactivates rather than hard-deletes, since historical attendance records reference a geofence by id.
- `manual` check-in tightened back to HR/Admin-only now that GPS is a standard employee path.
- **Verified**: 155 Jest tests (up from 137).

## [Phase 5] — Attendance

**Added** — `modules/attendance/`: self-service check-in/out + breaks, HR/Manager reporting, Excel/PDF export, and a two-track correction workflow (direct HR edit, and employee-request → manager/HR-approve).

- Late/overtime/half-day math ran against one hardcoded default shift this phase (09:00, 8h day) — replaced with real per-employee shift lookups in Phase 10.
- Only `method: 'manual'` was implemented; `gps`/`qr`/`face` were accepted by the Phase 2 schema but explicitly rejected with `METHOD_NOT_AVAILABLE` rather than silently no-op'ing.
- Both correction paths are audit-logged through a new fire-and-forget `audit.service.ts` — a failed audit write logs loudly but never fails the request it's describing.
- **Verified**: 137 Jest tests (up from 98).

## [Phase 4] — Employee Management

**Added** — `modules/employees/`: full CRUD, profile image + document upload (Multer memory storage → Cloudinary, no local disk).

- RBAC split deliberately: whole-role gates (list/search/create/delete) live at the route via `requireRole`; per-resource scoping (a Manager sees only their team; an employee can self-edit only `phone`/`address`/`emergencyContact`) lives in the service layer.
- `employeeCode` generation uses the standard MongoDB atomic-counter pattern, safe under concurrent creates.
- Employee creation is two sequential writes (User, then Employee), not a transaction — a documented v1 trade-off, not a hidden one.
- **Verified**: 98 Jest tests (up from 66).

## [Phase 3] — Authentication

**Added** — `modules/auth/`: register, login, JWT access + rotating refresh tokens, reuse-detection, logout, forgot/reset password, change password, `GET /me`.

- **Real bug caught by tests**: two refresh tokens signed for the same user within the same second were byte-identical (JWT `iat`/`exp` have second granularity). Fixed by adding a random `jti` to every signed token.
- The `User` schema tracks one active refresh-token hash per user (single session) — logging in on a new device ends the old session. Multi-device sessions would need a `sessions` sub-collection; a documented v2 item.
- **Verified**: 66 Jest tests (up from 31).
