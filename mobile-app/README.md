# AI Management System — Mobile App

Flutter employee app: GPS/QR/Face attendance, offline sync, leave, shifts, payslips. See [../docs/architecture/](../docs/architecture/) for the full design.

## Stack
Flutter · Clean Architecture (data/domain/presentation) · Riverpod · Dio · GoRouter · Hive + flutter_secure_storage (offline queue + token storage)

## Setup

```bash
flutter --version                 # confirm the SDK is installed (3.24+)
flutter pub get
flutter analyze
flutter test
flutter run
```

`android/` and `ios/` were generated by `flutter create . --org com.aimanagementsystem --platforms=android,ios` — a one-time step that adds the missing platform folders without touching existing Dart source, run once real Flutter tooling became available (this scaffold started out hand-written, without a Flutter SDK in that original environment, so those folders didn't exist yet at first). Re-run it yourself only if you delete `android/`/`ios/`; it's idempotent against everything else.

### Auth flow
- `DioClient` (`core/network/dio_client.dart`) attaches the access token to every request and, on a `401`, calls `/auth/refresh` once and retries — mirrors the admin dashboard's axios interceptor and [docs/architecture/07-authentication-flow.md](../docs/architecture/07-authentication-flow.md).
- Tokens + a minimal cached user profile live in `flutter_secure_storage` (Keychain/Keystore) — never in plain SharedPreferences.
- On launch, `AuthController` reads the cached session (no network round trip) to decide `/splash` → `/` or `/splash` → `/login`, via `core/router/app_router.dart`'s redirect guard.

### Attendance (GPS check-in)
- `LocationService` (`core/services/location_service.dart`) wraps `geolocator`: checks/requests permission, then reads a high-accuracy GPS fix — the only place the plugin is touched directly, mirroring `SecureStorageService`'s wrap of `flutter_secure_storage`.
- `AttendanceRepository.checkInWithGps()` composes that position with `POST /attendance/check-in` (`method: 'gps'`); check-out's location is best-effort (a revoked permission or disabled GPS between check-in and check-out doesn't block it — the field is optional server-side too).
- The screen shows today's status (not checked in / checked in at HH:mm / checked out, with worked hours), a single Check In/Check Out button that swaps based on that status, and a pull-to-refresh history list from `GET /attendance/me`.
- GPS was the first check-in method built, needing no new native capability beyond a location permission. QR and Face check-in followed in later passes — see [QR Check-In](#qr-check-in) and [Face Check-In](#face-check-in) below.
- Adding `geolocator` surfaced two real build bugs, both found by reproducing the CI failure locally (`flutter build apk --debug`) once GitHub's log API turned out to require auth this environment doesn't have:
  1. `minSdkVersion` below 26 needs `coreLibraryDesugaringEnabled true` plus the `desugar_jdk_libs` dependency — geolocator's own documented Android requirement.
  2. `geolocator_android`'s own `build.gradle` reads `flutter.compileSdkVersion` directly — a pattern from Flutter's older apply-script Gradle mechanism that used to inject that property onto every subproject automatically. This project's newer declarative plugin loading (`dev.flutter.flutter-gradle-plugin` applied only inside `:app`'s own build.gradle) doesn't do that anymore, so the property genuinely doesn't exist for a library subproject — fixed with a small compatibility shim in the root `android/build.gradle` (excluding `:app` itself, which needs its own real plugin-provided extension untouched).
  Also pinned `geolocator` below `14.0.0`: `geolocator_android` 5.x's Dart code calls `Color.toARGB32()`, a `dart:ui` API this project's pinned Flutter 3.24.0 doesn't have yet.

### Leave (apply/cancel/balance)
- Mirrors Attendance's shape: data/domain/presentation, a `Result<T>`-returning `LeaveRepository`, one controller loading leave types + balance + history concurrently on open.
- The apply form is a modal bottom sheet (`ApplyLeaveSheet`), not a separate route — four fields didn't justify a full-screen push. Overlap/balance/business-day validation all happens server-side; the sheet just surfaces whatever message comes back.
- `LeaveEntity.isCancellable` mirrors `leave.service.ts#cancel`'s exact server-side rule (pending is always cancellable; an approved one only if it hasn't started yet) so the Cancel button only ever appears where the server would actually allow it — the server re-checks regardless.

### Payslips (list + download)
- `GET /payslips/:id/pdf` is the one binary response in the whole API — `PayslipRemoteDataSource.downloadPayslipPdf` fetches it as raw bytes (`ResponseType.bytes`), and `PayslipRepositoryImpl` writes them to the app's documents directory via `path_provider` (a first-party Flutter-team plugin — no permissions, no `flutter.compileSdkVersion`-style Gradle surprises like geolocator's, confirmed by checking its own `android/build.gradle` before adding it).
- The save-confirmation `SnackBar` now has a real "Open" action, via `FileOpenerService` (`core/services/file_opener_service.dart`) wrapping `open_filex` — the one place that plugin is touched, mirroring `LocationService`'s wrap of `geolocator`. Its own Android manifest bundles a `FileProvider` declaration with a unique authority (`${applicationId}.fileProvider.com.crazecoder.openfile`), so no manual manifest changes were needed here — confirmed by reading the plugin's own `AndroidManifest.xml` before adding it, same Gradle-risk-auditing habit as every other plugin in this project. Doesn't auto-open on download completion, deliberately — the user taps "Open" if they want to, rather than an app-initiated action interrupting them uninvited. A "no app installed for PDFs" or similar failure shows its own follow-up `SnackBar` rather than failing silently.

### Notifications (inbox)
- `GET /notifications/me` fetches a single page (`limit: 50`) rather than full pagination UI — a documented scope cut, not an oversight; a real feed with true infinite scroll can follow if the inbox ever needs more than that at once.
- No broadcast composer here — sending one (`POST /notifications/broadcast`) is Super Admin/HR only and already built on the admin dashboard; this app is the self-service inbox side only.
- `NotificationState.unreadCount` derives from the currently-loaded list rather than a separate counter endpoint (the backend doesn't have one), same reasoning as the admin dashboard's Topbar badge.

### Offline Sync (attendance queue)
- `AttendanceRepositoryImpl.checkInWithGps()`/`checkOut()` catch a `NetworkException` specifically (as opposed to every other failure type) and enqueue the punch into `OfflineQueueService` — a Hive `Box<Map>` keyed by a client-generated id, no generated `TypeAdapter` (this project has no `build_runner` step; Hive natively stores plain Maps of primitives).
- Returns `OfflineQueuedFailure` in that case — a real `Failure` subtype, deliberately, so it fits `Result`'s two-branch shape without inventing a third `Result` case, but one `AttendanceController` pattern-matches on to show neutral "queued, will sync automatically" text instead of a red error banner.
- `ConnectivityService.onConnected` (wrapping `connectivity_plus`) emits only on actual offline→online transitions, not every connectivity change, so `SyncService` doesn't fire a sync attempt on every wifi/cellular handoff while already online.
- `SyncService.syncPending()` posts the whole queue to `POST /attendance/sync` in one batch and removes every result — `applied`, `duplicate`, or a definitive `conflict` — since retrying a business-rule conflict with the same stale data would just fail identically again (matches the backend's own `applySyncPunch` semantics, see attendance.service.ts). Starts once, from `syncServiceProvider`'s body, the first time `HomeScreen` reads it — a `Provider` body only runs once per app lifetime, so this is a clean way to guarantee "start exactly once, right after the user is authenticated" without a dedicated app-shell widget.
- Both directions queue on a `NetworkException`: check-in (any of GPS/QR/Face) and check-out. Check-out's *location* is separately best-effort (see the Attendance section above — a revoked permission doesn't block the request), but the request itself, once attempted, queues on failure exactly like check-in does.

### QR Check-In
- `QrCheckInScreen` owns a `MobileScannerController`/`MobileScanner` directly (`mobile_scanner`) — the only place that plugin is touched, same one-plugin-one-wrapper discipline as `CameraService`/`FaceDetectionService`. Unlike Face check-in, there's no multi-step capture pipeline to justify a separate Riverpod controller/state: decoding a barcode is a single event, so the screen forwards the scanned string straight to the existing `AttendanceController.checkInWithQr()` — the same controller GPS and Face check-in already submit through.
- The scanned value is the exact raw token the backend's `qrService.generate` encoded into the QR image in the first place — no parsing, no re-encoding, just read-back-and-forward to `POST /attendance/check-in` (`method: 'qr'`).
- Offline-queue fallback exists for symmetry with GPS/Face, but is honestly less useful here: a QR token is time-boxed server-side (`QR_DEFAULT_VALID_MINUTES`), and validation checks that window against "now" at sync time, not the original scan time — see `AttendanceRepositoryImpl.checkInWithQr()`'s own doc comment. An outage that outlasts the token's validity window means the eventual sync attempt comes back `QR_EXPIRED`, which `SyncService` already treats as a terminal (non-retried) result rather than looping on it forever.
- Adding `mobile_scanner` surfaced four more real Gradle bugs beyond geolocator's two, all found the same way (a local `flutter build apk --debug` reproduction, since GitHub's log API needs auth this environment doesn't have) and all now fixed and locally verified end-to-end (the debug APK actually built, past the previous Windows `jlink` wall too):
  1. Its transitive `androidx.camera:camera-camera2`/`camera-lifecycle` (CameraX) require **AGP 8.6.0+**, but `android/settings.gradle` pinned 8.1.0 — bumped, which in turn required bumping the Gradle wrapper itself to 8.9 (AGP 8.6.0's minimum).
  2. `mobile_scanner` itself requires **compileSdk 36** (the highest requirement among every plugin here — SDK levels are backward-compatible, so the highest one wins) — `android/app/build.gradle`'s `compileSdk` is now hardcoded to `36` instead of `flutter.compileSdkVersion`, the same override pattern already used for the AGP-driven bump.
  3. `androidx.camera:camera-video` declares **`minSdkVersion 23`** in its own manifest — the manifest merger fails outright if the app declares anything lower, so `minSdk` is now hardcoded to `23` (was `flutter.minSdkVersion`, 21). This is a real, documented trade-off: it drops official support for Android 5.0/5.1 (API 21–22) devices, not just a build-config tweak.
  4. The Kotlin sources `mobile_scanner` ships are compiled against **Kotlin 2.2.20**, but `android/settings.gradle` centrally pinned the whole project's `org.jetbrains.kotlin.android` plugin at 1.8.22 — every module using that plugin ID resolves to the centrally-declared version regardless of what an individual plugin's own `buildscript` block requests, so the fix had to happen in `settings.gradle`, not `mobile_scanner`'s own files (Flutter's own build error named this exact file as the fix point).
  Also bumped `ndkVersion` to `26.1.10909125` (a `flutter build` *warning*, not a hard failure, but every native plugin here already wanted it — NDK versions are backward-compatible, so satisfying the highest requirement satisfies them all).

### Face Check-In
- `CameraService` (wraps `camera`) and `FaceDetectionService` (wraps `google_mlkit_face_detection`) are the only two places those plugins are touched directly — everything else in `features/face/` works against this app's own `DetectedFace`/`Point2D` types.
- **Liveness is real**: `FaceCheckInController.start()` captures a short burst of still frames (not a single photo) while the user is asked to blink, runs face detection on each, and `BlinkLivenessChecker` — pure, unit-tested decision logic — requires a genuine open→closed→open transition across the sequence before proceeding. A printed photo or a frozen video frame reads as permanently open (or occluded) and can never produce that transition.
- **The embedding is *not* real** — ⚠️ see `GeometricEmbeddingGenerator`'s own doc comment for the full reasoning. In short: a trained FaceNet/MobileFaceNet `.tflite` model can't be bundled or verified in this environment (no GPU, no way to download/validate a model file), the same constraint the backend's own `faceEmbedding.provider.ts` already documents for server-side registration. Rather than add `tflite_flutter` around nothing real, this generates a deterministic 67-number vector from the detected face's actual landmark geometry (normalized positions + pairwise distances + eye-open probabilities) — a real function of a real detected face, unlike the backend's byte-hash placeholder, but not something that will reliably match the same person across different photos the way a trained model would.
- `AttendanceRepository.checkInWithFace()` mirrors `checkInWithGps()` exactly, including offline-queue fallback on a `NetworkException` (via the same `PendingPunch`, now carrying `faceEmbedding`/`livenessPassed` too).
- Face **registration** now has its own screen — see below — closing the mismatch this section used to flag as a Known Limitation.

### Face Registration
- `FaceRegistrationScreen` (reached from a new "Face Registration" card on `HomeScreen` — there's no Profile/Settings screen yet for it to live under instead) captures up to 5 still frames, keeps the ones with exactly one clearly-detected face, and runs each through the *same* `GeometricEmbeddingGenerator` check-in uses.
- Submits the collected embeddings (3–5, same bounds as the backend's `MIN_REGISTRATION_IMAGES`/`MAX_REGISTRATION_IMAGES`) to `POST /face/register-embeddings` — a plain JSON body, no image upload, matching the on-device-privacy rationale in `docs/architecture/06-tech-stack-justification.md`.
- No liveness check on this path, deliberately: `registerFaceEmbeddingsSchema` on the backend doesn't require one, and a registration photo isn't asserting "a live person is present right now" the way a check-in is.
- `FaceRegistrationController` loads `GET /face/registration-status` on open, so the screen shows "already registered" (with a photo count and last-updated time) rather than assuming a blank slate — re-registering is allowed and simply replaces the reference set, same as the image-upload path already did.
- **This is the piece that actually closes the registration/check-in mismatch** — see Known Limitations below for exactly how far that goes.

### Shifts
- `ShiftScreen` (a "My Shift" card on `HomeScreen`) is read-only — the mobile app was never going to need shift *management* (that's the admin dashboard's Super Admin/HR-only screen); an employee just needs to see their own assigned working hours.
- Fetches `GET /shifts/me`, which the backend already resolves down to "the assignment effective today, if any" (`shiftAssignmentService.getMyShift`) — so unlike `AttendanceEntity.isSameDayAs`/`isCheckedIn`, there's no client-side "is this still effective" logic to duplicate; `ShiftAssignmentEntity` is a flat mirror of the server's `ShiftAssignmentDTO`.
- `assignment: null` is a real, valid state (no shift currently assigned — attendance falls back to the standard default schedule server-side), not an error; the screen shows a plain explanatory message rather than treating it as a failure. `ShiftState.copyWith`'s `clearAssignment` flag exists specifically so a refresh that goes from "had a shift" to "no longer assigned one" actually clears the stale value instead of `??` silently keeping it — the same nullable-field problem `PayslipState.copyWith`'s `clearDownloadingId` already solved once.
- No new native dependency.

## Known Limitations
- **The registration/check-in embedding mismatch is closed only going forward, not retroactively.** Anyone who registers (or re-registers) via this app's new Face Registration screen gets embeddings from the same `GeometricEmbeddingGenerator` check-in uses, so they'll cosine-match correctly. An employee who was *only* ever registered through the original server-side photo-upload path (`POST /face/register`, still live, still using its own documented byte-hash placeholder) still has hash-based reference embeddings on file — those won't match a geometry-based check-in embedding until that employee re-registers through this screen. No code changes would fix this; it's a one-time re-enrollment gap for anyone already registered the old way.
